# Passim：手机端优先与外部 Agent 接入

> 日期：2026-11-11  
> 状态：产品方向草案。先沿此方向完善文档；具体交互、接口和实施范围仍需逐项确定。  
> 本文区分已有基础与后续规划，不表示规划中的功能已经上线，也不改变现有 API 的行为。

## 1. 定位与本轮选择

Passim 帮用户在自己的设备和服务器上搭建、使用并维护个人服务。后续优先强化手机端与外部 AI Agent 的连接，让用户既能用自然语言交代事情，也能随时查看状态、使用服务和处理需要自己决定的事项。

本轮确定的方向：

- **手机端是主要日常入口。** 优先服务于查看结果、使用常用服务、分享、关注异常和批准操作。
- **外部 Agent 是任务入口之一。** 用户继续使用熟悉的助手；Passim 提供受控能力，不要求用户先在 Passim 内选择模型或填写模型 API Key。
- **Web 保留必要职责。** 后续弱化普通用户对 Web 的依赖，保留首次配置、复杂配置、高级管理和恢复访问，不立即删除现有页面。
- **状态与控制长期可见。** 用户交代任务后，不必反复询问助手才知道进展，也不必通过聊天才能完成每一次常用操作。

首发仍以现有 Docker 节点为基础。NAS、家用服务器、路由系统及更多服务属于后续适配方向，需分别验证。

## 2. 当前基础与规划边界

| 能力 | 已有基础 | 仍需完成或验证 |
|---|---|---|
| 服务端 | Go API、SQLite、Docker 管理、模板、Stack、多节点 | 用户目标与底层操作的关联、服务端细粒度授权及操作审计 |
| 手机端 | Expo 54 / React Native、服务与节点管理界面 | 以日常使用为中心的首页、统一任务中心、Agent 连接管理 |
| Web | 嵌入式管理界面、高级模式 | 与手机端分工、恢复路径和功能取舍 |
| 任务与状态 | 持久化任务、任务查询、部署进度、SSE | 跨入口的持续任务记录、断线补偿、审批和结果验证 |
| AI 接入 | TypeScript stdio MCP，可由桥接进程调用节点 REST API | 普通用户配对、受限授权、远程 MCP、客户端兼容验证 |
| 通知与恢复 | 有相关依赖和现有运行基础 | 完整通知链路、备份恢复体验及真机验收 |

已有依赖、接口或单项测试不等于完整产品体验。远程 MCP、Agent 权限管理、统一任务中心和手机内置系统级连接均不能作为已交付功能宣传。

## 3. 手机端的主要结构

以下为建议的信息结构，最终导航与交互待设计验证。

### 首页：现在有什么需要关注

按用户行动组织内容：

1. **需要处理**：待批准操作、服务异常、需要补充的信息。
2. **常用服务**：直接打开、连接、获取配置或分享的入口。
3. **正在进行**：任务当前阶段、最近变化、阻塞原因与下一步。
4. **设备概况**：节点可达性、容量或资源异常；详细指标进入设备页。

正常运行的信息保持简洁。CPU、内存和网络图表用于解释问题，不占据默认首页的主要空间。尚未实现的能力不显示为可用按钮。

### 服务：部署之后仍然有用

服务页持续回答：能否使用、入口在哪里、数据放在哪里、谁能访问、最近是否发生变化。

优先提供与该服务相关的常用操作，例如连接、打开、分享与撤销分享。备份、恢复等入口应在对应能力实际实现后提供。保留标准协议、配置导出和第三方客户端出口，避免把所有第三方产品界面都装进 Passim。

**服务状态与任务状态分开。** “部署任务已完成”和“服务目前离线”可以同时成立。不能用过去一次任务成功替代当前可用性检查。

### 任务：交代后不用反复询问

一个用户目标可以对应多个底层操作。例如“部署并分享一个服务”可能包含检查节点、部署、生成客户端配置、验证和分享。

每个任务至少应显示：

- 用户目标、发起入口与涉及的节点或服务。
- 当前阶段、最近更新时间和最近一条有效进展。
- 阻塞原因、下一步，以及下一步由用户、Agent 还是 Passim 执行。
- 结果入口、验证结论和可用的恢复方式。

没有可靠进度依据时只显示阶段，不编造百分比。等待用户、等待 Agent、执行中和连接中断应明确区分。取消仅在底层操作支持时提供，不能让界面宣称取消而操作继续执行。

### 设备与设置：按需深入

设备页保留节点状态和资源信息。容器、Stack 等继续属于高级操作。设置中组织 Agent 连接、授权、通知和恢复访问，避免普通用户为了使用服务而理解全部基础设施概念。

## 4. 客户端、Agent 与服务端分工

| 部分 | 主要职责 |
|---|---|
| 手机端 | 日常服务入口、真实状态、任务结果、必要批准和连接管理 |
| 外部 Agent | 理解目标、查询能力、提出方案、协调步骤和解释异常 |
| Passim 服务端 | 权限校验、确定性执行、任务记录、状态采集、审计与恢复 |
| Web | 初始配置、复杂配置、高级管理与手机端不可用时的恢复入口 |

手机端不承担必须持续在线的执行器或 MCP 桥接职责。锁屏、切换网络、系统回收 App 进程，不应中断已经交给服务端执行的操作。

stdio MCP 可以运行在用户选择且已授权的电脑或服务器上，通过 HTTPS 访问 Passim 节点，不要求运行在手机或节点本机。桥接宿主仍需验证网络、凭据存储和运行可靠性；一次临时启动成功不等于常驻托管。

远程 MCP 的部署位置、认证方式以及家庭网络可达性仍需设计。应逐个验证目标 Agent 客户端，不能把“支持 MCP”描述成所有客户端均可直接连接。

## 5. 所有入口共享任务与状态

手机按钮、Web 和外部 Agent 发起的操作应进入同一套任务与事件记录，并关联发起者、目标、资源和实际变更。聊天可以解释过程，但不能成为唯一的状态存储。

实施时需要补充：

- 用户目标与底层操作的关联标识，区分整体目标与单步执行结果。
- 事件顺序、去重和重连补偿；客户端恢复连接后重新获取权威状态。
- 重复提交的幂等处理，特别是网络切换、重试和重复批准。
- 明确的更新时间与离线标记，不把缓存展示成实时状态。
- 对“容器启动”之外的服务可用性验证；无法验证时清楚说明。
- 验证现有队列的失败恢复、重试和重启行为，不假设持久化本身已解决全部问题。

已提交到 Passim 的操作由服务端继续管理；尚待 Agent 规划的工作在 Agent 离线时应显示等待状态。Passim 不负责接管助手在邮件、日程或其他系统中的所有任务。

## 6. 安全连接与操作批准

建议手机端提供“连接我的 AI”流程：选择客户端、完成配对、确认范围、查看近期操作、撤销连接。具体协议与交互尚未实现。

安全要求：

- 至少按节点、能力和有效期表达授权；默认从有限只读能力开始，避免让所有 Agent 持有完整管理员密钥。
- 查看状态、部署、维护、分享与所有者级操作应能区别授权。凭证、原始日志、连接配置和文件内容需要单独的数据访问边界。
- 高影响操作的批准必须绑定具体动作、目标、关键参数和有效期，由服务端校验。模型传入的 `confirm: true` 不能替代用户批准。
- 撤销连接、批准过期、重复提交及权限变化都需在执行前重新校验。不能把通知点击直接当作充分授权。
- 凭据通过安全配对或受保护的配置渠道提供，不要求用户把管理员密钥或会话令牌粘贴到聊天。
- 审计记录可回答谁通过哪个入口改变了什么，以及执行结果；日志和通知避免包含密钥或敏感配置。

当前 MCP 使用管理员 API Key 换取 JWT，尚没有完整的服务端只读权限和上述批准模型。新增远程入口前应先明确并落实这些边界。安全网页登录建立浏览器会话，也不意味着命令行 MCP 已自动获得可用凭据。

## 7. 通知、可靠性与恢复

主动通知优先用于需要决定、失败、服务异常或重要完成结果。合并重复告警，并让通知直接进入相关任务或服务。普通状态变化更新界面即可，避免每个底层事件都打扰用户。

验收应覆盖 App 进入后台、断网与重连、重复点击、批准过期、Agent 断开、节点重启和部分步骤失败。服务端任务、通知是否送达、用户是否查看是不同状态，不能混为一谈。

保留 Web 恢复入口。手机丢失、无法登录、App 更新或分发受阻时，用户仍需查看和管理自己的服务。手机内置 VPN 等能力另行评估原生组件、系统权限、客户端兼容和分发要求，首阶段可先使用第三方客户端。

## 8. 渐进实施与待决定事项

建议先选择一个已有模板支持的场景，完成从交代目标到实际使用的手机闭环。安全连接或文件共享都是候选，首个场景尚未确定。

阶段、验收与暂缓范围见[手机端与 Agent 路线](mobile-first-roadmap.md)。

仍需决定：

1. 首个样板服务、目标用户与目标 Agent 客户端。
2. 首页与底部导航的最小结构，手机端直接承担哪些日常使用任务。
3. 任务关联、事件同步、服务可用性验证的接口方案。
4. Agent 授权范围、批准规则和凭据撤销方式。
5. 远程 MCP 的部署方式、可达性与稳定运行责任。
6. 通知渠道、异常判定、恢复路径及数据保留规则。

本轮只记录方向，不设未经验证的交付日期、成功率目标或跨平台兼容承诺。现有功能规格在完成对应评审前继续作为实现参考。
